# Создатель спринтов

Превращает книги пользователя и его цель в курс-спринт на 7–14 дней. Каждый день курса состоит из истории, инструмента, задания в реальной жизни с дедлайном, квеста (если он предусмотрен) и напоминания о сквозной практике. Курс собирается за четыре этапа. После каждого пользователь читает результат, правит и утверждает его.

## Перед началом

Прочитай [references/methodology.md](references/methodology.md) целиком. Там роль и голос автора, устройство дня, стиль, запреты, границы метода и правило утверждения. Методология действует на всех этапах.

Файлы этапов написаны от лица пользователя: «я» в них означает пользователя, «ты» означает тебя. Выполняй текст после первой черты как его задание на этот этап.

## Рабочая папка

Спроси, где вести спринт. По умолчанию это папка `sprint/` в текущем каталоге.

| Файл | Что в нём | Когда появляется |
|---|---|---|
| `params.md` | параметры спринта и список книг | шаг 0 |
| `result_1_recon.md` | утверждённая разведка | этап 1 |
| `result_2_architecture.md` | утверждённый каркас | этап 2 |
| `result_3_plan.md` | утверждённый план по дням | этап 3 |
| `day_01.md`, `day_02.md`, … | утверждённые тексты дней | этап 4 |

Если папка уже есть, прочитай её и продолжи с первого этапа, у которого ещё нет утверждённого файла.

Если писать файлы нельзя или они не сохраняются между сессиями (например, новый чат в claude.ai), выдавай утверждённый итог целиком, называй имя файла и попроси пользователя сохранить его и приложить к следующему этапу.

## Шаг 0. Параметры и книги

1. Возьми блок «Параметры спринта» из методологии и заполни его вместе с пользователем: спроси про пустые поля, размытую цель заостри до конкретной.
2. Узнай, где лежат книги, и добавь к параметрам строку `Книги:` со списком файлов.
3. Проверь, что каждая книга читается. Большую книгу читай частями. Если файл не открылся целиком (скан, неподдерживаемый формат, обрезка), скажи, что удалось прочитать, и предложи конвертировать его в TXT или Markdown.
4. Если тема или цель из раздела «Границы метода», один раз предупреди. Решение за пользователем.
5. Покажи параметры и дождись «утверждаю». Тогда запиши их в `params.md`, первая строка `Статус: УТВЕРЖДЕНО`.

## Этапы

| Этап | Инструкция | Итог |
|---|---|---|
| 1. Разведка | [references/stage-1-recon.md](references/stage-1-recon.md) | `result_1_recon.md` |
| 2. Архитектура | [references/stage-2-architecture.md](references/stage-2-architecture.md) | `result_2_architecture.md` |
| 3. План | [references/stage-3-plan.md](references/stage-3-plan.md) | `result_3_plan.md` |
| 4. Урок, по одному дню | [references/stage-4-lesson.md](references/stage-4-lesson.md) | `day_NN.md` |

Справочник механик [references/mechanics.md](references/mechanics.md) нужен на этапах 2 и 3.

После каждого утверждения показывай чек-лист и отмечай пройденное:

```
- [ ] 0. Параметры → params.md
- [ ] 1. Разведка → result_1_recon.md
- [ ] 2. Архитектура → result_2_architecture.md
- [ ] 3. План → result_3_plan.md
- [ ] 4. Дни → day_01.md … day_NN.md
```

## Правила

- Один этап за раз. Покажи результат и жди правок. Следующий этап начинай только после «утверждаю».
- На «утверждаю» запиши итоговую версию со всеми правками в файл этапа. Первая строка файла: `Статус: УТВЕРЖДЕНО`.
- Каждый этап опирается только на утверждённые файлы. Решения из переписки, которых нет в файлах, не используй.
- Если параметры уточнились по ходу работы, обнови `params.md` и покажи пользователю, что изменилось.
- На этапе 4 пиши дни по порядку: следующий день без утверждённого `day_NN.md`, если пользователь не назвал другой. Входные данные дня заполни сам из `result_3_plan.md` и покажи их вместе с планом урока на предполётной проверке. Полный текст дня пиши после «ок».

## Если пользователь проходит курс с тобой

- Выдавай день N+1 только после того, как пришёл результат задания дня N (стоп-лок).
- Если участнику плохо, действует раздел «Границы метода» из методологии: давление снимается сразу.
